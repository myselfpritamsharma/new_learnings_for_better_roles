def checkInclusion(self, s1: str, s2: str) -> bool:
    left = 0
    window = {}
    need = {}

    for ch in s1:
        need[ch] = need.get(ch, 0) + 1

    for right in range(len(s2)):
        window[s2[right]] = window.get(s2[right], 0) + 1

        if right - left + 1 > len(s1):
            window[s2[left]] -= 1
            if window[s2[left]] == 0:
                del window[s2[left]]
            left += 1

        if window == need:
            return True

    return False

def characterReplacement(self, s: str, k: int) -> int:
    max_freq = 0
    freq = {}
    left = 0
    max_len = 0

    for right in range(len(s)):
        freq[s[right]] = freq.get(s[right], 0) + 1
        max_freq = max(max_freq, freq[s[right]])

        window_size = right - left + 1
        replacement_needed = window_size - max_freq

        if replacement_needed > k:
            freq[s[left]] -= 1
            left += 1

        max_len = max(max_len, right - left + 1)

    return max_len
Takeaway: Expand, calculate replacements, shrink if invalid, then measure the repaired window.

Choice: Token Bucket.

Reason 1: It allows controlled bursts while enforcing an average request rate.

Reason 2: It is memory efficient. Store only the current token count and last refill time per user.

Task 3 Solution: LEFT JOIN Users and Orders

INNER JOIN: Returns only users who have at least one matching order.

LEFT JOIN: Returns every user. If a user has no matching order, the order columns are NULL.

SELECT
    u.name AS user_name,
    o.amount
FROM Users AS u
LEFT JOIN Orders AS o
    ON o.user_id = u.id;

Use LEFT JOIN because the requirement says to include users with no orders.

Common mistake: Adding an order filter in the WHERE clause can remove users with no orders and accidentally make the query behave like an inner join.

📘 Theory: Valid Palindrome (Two-Pointer)

How to think: A palindrome reads the same from both ends. So instead of building a cleaned copy of the string, compare characters directly from the outside in, skipping anything that is not a letter or digit.

Brute-force approach: Build a new string containing only lowercase alphanumeric characters, then compare it with its reverse.

cleaned = [c.lower() for c in s if c.isalnum()]
return cleaned == cleaned[::-1]

Why brute force is insufficient: It is not actually wrong for this problem size, but it uses O(n) extra space for the cleaned list and its reverse. The two-pointer approach solves it in O(1) extra space, which interviewers expect you to reach.

Optimal pattern/approach: Two-Pointer. Keep left at the start and right at the end. Skip non-alphanumeric characters on either side. Compare the remaining characters case-insensitively. Stop as soon as a mismatch is found.

Step-by-step walkthrough: For "A man, a plan, a canal: Panama", skip spaces/commas/colons, compare 'A' vs 'a' (equal after lowering), move both pointers inward, and repeat until they cross without any mismatch.

Edge cases to test: empty string, single character, all non-alphanumeric characters (e.g. ".,!"), mixed case, and strings with only one mismatch near the middle.

Time complexity: O(n) — each character is visited at most once.

Space complexity: O(1) — only two pointers are used, no extra buffers.

Interview language: "I compare from both ends inward, skipping non-alphanumeric characters, so I never need to allocate a cleaned copy of the string."

✅ Solution: Valid Palindrome

def isPalindrome(s: str) -> bool:
    left, right = 0, len(s) - 1
    while left < right:
        if not s[left].isalnum():
            left += 1
        elif not s[right].isalnum():
            right -= 1
        elif s[left].lower() != s[right].lower():
            return False
        else:
            left += 1
            right -= 1
    return True
📘 Theory: 3Sum (Two-Pointer + Sorting)

How to think: You need all unique triplets that sum to zero. Fixing one number and searching for a pair that cancels it out turns a 3-number search into a 2-number search — which Two-Pointer solves in linear time once the array is sorted.

Brute-force approach: Try every triplet with three nested loops and check if it sums to zero, using a set to dedupe results.

for i in range(n):
    for j in range(i+1, n):
        for k in range(j+1, n):
            if nums[i]+nums[j]+nums[k] == 0:
                record sorted((nums[i], nums[j], nums[k]))

Why brute force is insufficient: O(n³) time, and deduping with a set adds overhead. For n up to 3000 (typical constraint) this is far too slow.

Optimal pattern/approach: Sort the array first. Fix nums[i] as the first number, then use Two-Pointer (left = i+1, right = n-1) to find pairs that sum to -nums[i]. Skip duplicate values at every level to avoid duplicate triplets.

Step-by-step walkthrough: For [-1,0,1,2,-1,-4] sorted → [-4,-1,-1,0,1,2]. Fix i=1 (-1), search with left=2, right=5: sum -1+2=1 > 1? adjust pointers based on comparison to target 1, finding (-1, -1, 2) and (-1, 0, 1). Skip repeated -1 at the outer loop to avoid duplicate triplets.

Edge cases to test: array with fewer than 3 elements, all zeros, all positive or all negative numbers (no valid triplet), and arrays with many duplicate values.

Time complexity: O(n²) — O(n log n) to sort, then O(n) two-pointer scan for each of the n fixed elements.

Space complexity: O(1) extra (excluding the output list); sorting may use O(log n) internally.

Interview language: "I sort first to enable two-pointer search, fix one element at a time, and skip duplicates at both the outer loop and the pointer level to avoid duplicate triplets."

✅ Solution: 3Sum 
class Solution:
    def threeSum(self, nums: list[int]) -> list[list[int]]:
        nums.sort()
        res = []

        for i in range(len(nums)):
            if i > 0 and nums[i] == nums[i - 1]:
                continue

            left, right = i + 1, len(nums) - 1

            while left < right:
                curr_sum = nums[i] + nums[left] + nums[right]

                if curr_sum == 0:
                    res.append([nums[i], nums[left], nums[right]])
                    left += 1
                    right -= 1

                    while left < right and nums[left] == nums[left - 1]:
                        left += 1
                    while left < right and nums[right] == nums[right + 1]:
                        right -= 1

                elif curr_sum > 0:
                    right -= 1
                else:
                    left += 1

        return res

Key lesson: Duplicate-skipping must run only after a match, comparing against the just-used value (nums[left-1], nums[right+1]) — never before the first sum check for a given i. And the pointer-movement for non-zero sums must be an elif/else, not a separate unconditional block, or a match gets double-counted with an extra unwanted shift.

📘 Theory: Sliding Window (Pattern Overview)

How to think: Instead of checking every substring/subarray, maintain a contiguous range [left, right] that always satisfies some invariant (no duplicates, valid frequency count, sum threshold, etc.). Expand with right; when the invariant breaks, shrink from left until it holds again.

Brute-force approach: Generate all substrings/subarrays with nested loops and check the condition for each one independently.

for i in range(n):
    for j in range(i, n):
        check substring s[i:j+1]

Why brute force is insufficient: This is O(n²) or worse (O(n³) if checking the condition itself takes O(n)). Sliding Window reuses state between iterations instead of recomputing it, dropping this to O(n).

Optimal pattern/approach: Two flavors — fixed window (constant size, e.g. len(s1) in Permutation in String) and variable window (grows/shrinks based on a condition, e.g. Longest Repeating Character Replacement, Minimum Window Substring).

Step-by-step walkthrough: Add s[right] to the window state → check if the invariant is violated → if so, remove s[left] and advance left until valid again → record/update the answer.

Edge cases to test: empty string, window larger than the string, all identical characters, target substring at the very start or end, and cases with no valid window at all.

Time complexity: O(n) — each pointer moves forward at most n times total, so no re-scanning.

Space complexity: O(k) — where k is the number of distinct characters tracked in the frequency map (often O(1) for fixed alphabets).

Interview language: "I maintain a window that always satisfies the invariant, expanding with right and repairing with left, so every character is processed in constant amortized time."

📘 Theory: Longest Substring Without Repeating Characters

How to think: You need the longest contiguous run of unique characters. Track how many times each character currently appears in the window; the window is valid as long as no character repeats.

Brute-force approach: For every starting index, extend as far as possible while checking a set for duplicates.

for i in range(n):
    seen = set()
    for j in range(i, n):
        if s[j] in seen:
            break
        seen.add(s[j])
        max_len = max(max_len, j - i + 1)

Why brute force is insufficient: O(n²) time because every starting index re-scans forward. For long strings this is too slow.

Optimal pattern/approach: Variable Sliding Window with a frequency map. Expand right; if the incoming character's count exceeds 1, shrink from left until it's back to 1.

Step-by-step walkthrough: For "abcabcbb", expand to "abc" (all unique, length 3). Adding the next 'a' creates a duplicate, so shrink left past the first 'a', leaving "bca". Continue this way, tracking the best length seen.

Edge cases to test: empty string, all identical characters (e.g. "aaaa"), all unique characters, single character, and strings with the longest unique run at the end.

Time complexity: O(n) — each index enters and leaves the window at most once.

Space complexity: O(k) — k is the number of distinct characters in the current window (at most the alphabet size).

Interview language: "I track character frequency in the window and shrink from the left the moment a duplicate appears, so each character is processed twice at most."

📘 Theory: Permutation in String

How to think: A permutation of s1 is any rearrangement with the exact same character counts. So instead of generating permutations, check whether any fixed-size window of s2 (size len(s1)) has the same character frequency as s1.

Brute-force approach: For every window of length len(s1) in s2, build a fresh frequency map and compare it with s1's frequency map.

for i in range(len(s2) - len(s1) + 1):
    window = Counter(s2[i:i+len(s1)])
    if window == need:
        return True

Why brute force is insufficient: Rebuilding the frequency map for every window costs O(k) each time, giving O(n·k) overall, where k = len(s1). This is wasteful because consecutive windows overlap almost entirely.

Optimal pattern/approach: Fixed-size Sliding Window. Slide the window by adding s2[right] and removing s2[left] incrementally, instead of rebuilding the map from scratch.

Step-by-step walkthrough: For s1 = "ab", s2 = "eidbaooo", slide a window of size 2 across s2. When the window becomes "ba", its frequency map {"b":1,"a":1} matches need, so return True.

Edge cases to test: s1 longer than s2, s1 and s2 identical, no matching window at all, and a match at the very end of s2.

Time complexity: O(n) — each character of s2 is added and removed from the window at most once.

Space complexity: O(1) — frequency maps are bounded by the fixed alphabet size (26 lowercase letters).

Interview language: "I maintain a fixed-size window and update its frequency map incrementally instead of recomputing it, so each character is touched a constant number of times."

📘 Theory: Longest Repeating Character Replacement

How to think: You want the longest window where, after replacing at most k characters, all characters become identical. A window is achievable if the count of "non-majority" characters (window length minus the highest single-character frequency) is at most k.

Brute-force approach: For every window, count the frequency of every character, find the max, and check if window_length - max_frequency <= k.

for i in range(n):
    for j in range(i, n):
        freq = Counter(s[i:j+1])
        if (j - i + 1) - max(freq.values()) <= k:
            max_len = max(max_len, j - i + 1)

Why brute force is insufficient: Recomputing frequency counts for every window is O(n²) or worse, since building each window's Counter costs O(n) in the worst case.

Optimal pattern/approach: Variable Sliding Window. Maintain a running frequency map and the highest frequency seen so far. Shrink only when window_length - max_frequency > k.

Step-by-step walkthrough: For "AABABBA", k=1: window "AABA" has length 4, max frequency 3 (character 'A'), so replacements needed = 1, which is within budget — valid. Extending further can force a shrink if replacements needed exceeds 1.

Edge cases to test: k = 0 (no replacements allowed, so answer is the longest run of one repeated character), k >= len(s) (whole string is always valid), single character, and all identical characters.

Time complexity: O(n) — one pass; max_freq never needs to decrease for correctness of the maximum length.

Space complexity: O(1) — frequency map bounded by 26 uppercase letters.

Interview language: "I track the highest character frequency in the window; the window is valid as long as the number of characters that would need replacing stays within k."

📘 Theory: Minimum Window Substring

How to think: You need the smallest window in s that contains every character of t with at least the required count. Expand until the window satisfies all requirements, then shrink from the left as much as possible while it stays valid — this repeatedly finds smaller valid windows.

Brute-force approach: For every pair of start and end indices, check whether that substring contains all required characters with sufficient counts.

for i in range(n):
    for j in range(i, n):
        if contains_all_required(s[i:j+1], t):
            track minimum length

Why brute force is insufficient: This is O(n²) windows, each costing up to O(n) or O(k) to validate — far too slow for long strings.

Optimal pattern/approach: Variable Sliding Window with a "formed vs required" counter. required = number of distinct characters needed; formed = how many of those currently meet their required count. Shrink while formed == required.

Step-by-step walkthrough: For s = "ADOBECODEBANC", t = "ABC", expand right until the window "ADOBEC" satisfies all of A, B, C. Then shrink from the left, dropping characters until removing one would break the requirement, recording the smallest valid window along the way. Continue until eventually finding "BANC".

Edge cases to test: t longer than s (impossible, return ""), t with duplicate characters (e.g. "AABC" needs two A's), no valid window exists, and the entire string s being the only valid window.

Time complexity: O(len(s) + len(t)) — building need costs O(len(t)); the two-pointer scan over s is O(len(s)).

Space complexity: O(k) — k is the number of distinct characters in t.

Interview language: "I track how many distinct required characters are currently satisfied; once all are satisfied I shrink from the left to find the smallest valid window before expanding again."

def lengthOfLongestSubstring(s: str) -> int:
    left = 0
    max_len = 0
    freq = {}

    for right in range(len(s)):
        freq[s[right]] = freq.get(s[right], 0) + 1

            left += 1

Open on GitHub

def minWindow(s: str, t: str) -> str:
    need = {}
    for ch in t:
        need[ch] = need.get(ch, 0) + 1

    left = 0
    min_word = ""
    min_len = float("inf")
    freq = {}
    required = len(need)
    formed = 0

    for right in range(len(s)):
        incoming = s[right]
        freq[incoming] = freq.get(incoming, 0) + 1

        if incoming in need and freq[incoming] == need[incoming]:
            formed += 1

        while formed == required:
            current_len = right - left + 1
            if current_len < min_len:
                min_len = current_len
                min_word = s[left:right + 1]

            outgoing = s[left]
            freq[outgoing] -= 1
            if outgoing in need and freq[outgoing] < need[outgoing]:
                formed -= 1
            left += 1

    return min_word

Idea: Two indices moving strategically to avoid nested loops (O(n) vs O(n²)).
Problems: Valid Palindrome, Two Sum II, Container With Most Water, 3Sum
Key: Works on sorted arrays or when order property helps.
Status: 🟡 Yellow (1/3 solved)
Day 1 Theory: Two-Pointer + Valid Palindrome
Core idea
Keep two pointers, usually left and right. Move them based on what the comparison tells you. This avoids checking all pairs.
When to use
Palindromes, sorted arrays, pair sums, reversing, container/water problems, or cases where both ends carry useful information.
Interview language
"I can solve this in one pass by maintaining two boundaries and moving only the pointer that cannot contribute to the answer."
Valid Palindrome reasoning:
  • Ignore characters that are not letters/digits using isalnum().
  • Compare normalized characters using lower().
  • If both match, move inward. If mismatch, return False.
  • If the pointers cross without mismatch, the string is a valid palindrome.
def isPalindrome(s: str) -> bool:
    left, right = 0, len(s) - 1

    while left < right:
        if not s[left].isalnum():
            left += 1
        elif not s[right].isalnum():
            right -= 1
        elif s[left].lower() != s[right].lower():
            return False
        else:
            left += 1
            right -= 1

    return True
Complexity: O(n) time, O(1) space.

Pattern 2: Sliding Window

Idea: Dynamic window expands/contracts to find optimal subarray/substring in O(n).
Problems: Longest Substring Without Repeating Characters, Minimum Window Substring
Key: Use HashMap to track state; each element added/removed at most once.
Status: 🟡 Yellow (3/4 solved)
Day 2 Theory: Sliding Window + Longest Substring Without Repeating Characters
Core idea
Maintain a valid range [left, right]. Expand using right; if the window becomes invalid, shrink using left.
When to use
Longest/shortest subarray or substring problems where the answer is a contiguous block.
Window invariant
For this problem: the current window must contain no duplicate characters.
Reasoning:
  • Add s[right] to the frequency map.
  • If s[right] now appears more than once, the window is invalid.
  • Move left forward until the duplicate is removed.
  • Update max_len only after the window is valid again.
class Solution:
    def lengthOfLongestSubstring(self, s: str) -> int:
        left = 0
        max_len = 0
        freq = {}

        for right in range(len(s)):
            freq[s[right]] = freq.get(s[right], 0) + 1

            while freq[s[right]] > 1:
                freq[s[left]] -= 1
                left += 1

            max_len = max(max_len, right - left + 1)

        return max_len
Common bug: When shrinking, decrement freq[s[left]], not freq[s[right]]. The left character is the one leaving the window.
Complexity: O(n) time, O(k) space, where k is the number of distinct characters.
Day 4 Theory: Longest Repeating Character Replacement

Problem: Given an uppercase string and integer k, find the longest substring that can be made one repeated character after at most k replacements.

Window rule: Let window_length be the current window size and max_frequency be the count of its most common character. Replacements needed are:

replacements_needed = window_length - max_frequency

The window is valid when replacements_needed <= k. If invalid, move left forward until it becomes valid.

Example: For "AABABBA" and k = 1, "AABA" has length 4 and maximum frequency 3, so it needs 1 replacement and is valid.

Common mistake: Comparing the number of distinct characters with k. The correct value is window length minus the highest frequency.

Complexity: O(n) time and O(1) space for the 26 uppercase letters.

Interview phrase: "I keep the largest window where all non-majority characters can be replaced within k operations."

📘 Theory Only: Minimum Window Substring

Problem: Find the smallest substring of s that contains every character of t, including duplicate counts.

Thinking model: Expand the right pointer until the window satisfies all requirements. Then shrink from the left while it remains valid. When it becomes invalid, expand again.

State: Track required frequencies, current frequencies, how many character requirements are satisfied, and the smallest valid window.

Common mistake: Checking only whether characters exist. If t = "AABC", the window needs two A characters.

Complexity: O(n) time and O(k) space, where k is the number of distinct required characters.

Interview phrase: "Once all required counts are satisfied, I minimize from the left before expanding again."

def minWindow(self, s: str, t: str) -> str:
    need = {}
    for ch in t:
        need[ch] = need.get(ch, 0) + 1

    left = 0
    min_word = ""
    min_len = float("inf")
    freq = {}
    required = len(need)
    formed = 0

    for right in range(len(s)):
        incoming = s[right]
        freq[incoming] = freq.get(incoming, 0) + 1

        if incoming in need and freq[incoming] == need[incoming]:
            formed += 1

        while formed == required:
            current_len = right - left + 1
            if current_len < min_len:
                min_len = current_len
                min_word = s[left:right + 1]

            outgoing = s[left]
            freq[outgoing] -= 1
            if outgoing in need and freq[outgoing] < need[outgoing]:
                formed -= 1
            left += 1

    return min_word
Complexity: O(n) time, O(k) space.

SOLID Principles (The Foundation)

1. Single Responsibility (SRP)

SRP: One Class, One Reason To Change

Meaning: A class should own one responsibility. If validation, database writes, email sending, and logging all live in one class, one change can break unrelated behavior.

Bad shape: UserService validates input, hashes password, inserts into DB, sends email, and logs events.

Good shape: Split into UserValidator, PasswordHasher, UserRepository, EmailService, and AuditLogger.

class UserService:
    def __init__(self, validator, hasher, repo, email_service):
        self.validator = validator
        self.hasher = hasher
        self.repo = repo
        self.email_service = email_service

    def register(self, email, password):
        if not self.validator.is_valid(email, password):
            return False
        password_hash = self.hasher.hash(password)
        self.repo.save(email, password_hash)
        self.email_service.send_welcome(email)
        return True

Interview line: "I separated responsibilities so validation, persistence, and notification can change independently and be unit tested separately."

2. Open/Closed (OCP)

OCP: Add New Behavior Without Modifying Stable Code

Meaning: Existing tested code should stay stable when new variants are added. Add classes, don't keep adding if/elif branches.

Bad shape: Cache.evict() has if policy == "LRU", elif policy == "LFU", elif policy == "FIFO".

Good shape: Use a strategy interface.

class EvictionPolicy:
    def evict(self, cache):
        raise NotImplementedError

class LRUEviction(EvictionPolicy):
    def evict(self, cache):
        pass

class LFUEviction(EvictionPolicy):
    def evict(self, cache):
        pass

class Cache:
    def __init__(self, capacity, eviction_policy):
        self.capacity = capacity
        self.eviction_policy = eviction_policy

Interview line: "Adding LFU or FIFO should not require modifying the cache core; I would inject the eviction strategy."

3. Liskov Substitution (LSP)

LSP: Subtypes Must Not Break Parent Contracts

Meaning: If code expects a parent type, every child type must behave safely under the same contract.

Bad shape: Penguin extends Bird but throws in fly(). Or ReadOnlyRepository implements save() but throws.

Good shape: Model behavior honestly. Use Movable, Flyable, ReadableRepository, WritableRepository.

class Logger:
    def write(self, message):
        raise NotImplementedError

class FileLogger(Logger):
    def write(self, message):
        pass

class ConsoleLogger(Logger):
    def write(self, message):
        pass

Interview line: "Any implementation of the interface should be usable without the caller needing special-case checks."

4. Interface Segregation (ISP)

ISP: Prefer Small Focused Interfaces

Meaning: Don't create one huge interface that forces every class to implement unused methods.

Bad shape: One DataStore interface with read, write, delete, scan, backup, restore. A read-only cache is forced to fake unsupported operations.

Good shape: Split by capability.

class Reader:
    def read(self, key):
        raise NotImplementedError

class Writer:
    def write(self, key, value):
        raise NotImplementedError

class ReadOnlyCache(Reader):
    def read(self, key):
        pass

Interview line: "I would expose only the capabilities each client needs, which keeps contracts smaller and implementations honest."

5. Dependency Inversion (DIP)

DIP: Depend On Abstractions, Not Concrete Classes

Meaning: High-level business logic should not create or depend directly on low-level infrastructure like MySQL, Redis, SMTP, or Kafka clients.

Bad shape: UserService directly creates MySQLDatabase(). Tests need MySQL, and switching DB requires code changes.

Good shape: Inject an abstraction.

class UserRepository:
    def save(self, user):
        raise NotImplementedError

class SqlUserRepository(UserRepository):
    def save(self, user):
        pass

class UserService:
    def __init__(self, repo: UserRepository):
        self.repo = repo

Interview line: "I depend on a repository abstraction so I can test with mocks and swap SQL/NoSQL implementations without touching business logic."

Today's LLD Theory: Rate Limiter

Rate Limiter Basics: What Problem Are We Solving?

A rate limiter controls how many requests a user, IP, API key, or tenant can make in a time interval. Example: 100 requests/minute/user.

  • Input: user ID / API key / IP + timestamp.
  • Decision: allow request or reject with HTTP 429 Too Many Requests.
  • State: request counters, timestamps, or token count per user.
  • Hard part: doing this fast and correctly under high traffic and distributed servers.
Fixed Window Counter

Idea: Count requests in a fixed time bucket, like 10:00:00 to 10:00:59. Reset when the next minute starts.

key = user_id + current_minute
count = redis.incr(key)
if count == 1:
    redis.expire(key, 60)
return count <= 100

Pros: Very simple, memory efficient, fast in Redis.

Cons: Boundary burst problem. A user can send 100 requests at 10:00:59 and 100 more at 10:01:00, effectively 200 requests in 2 seconds.

Use when: Limits do not need high precision.

Sliding Window Log

Idea: Store timestamps of each request. For every request, remove timestamps older than 60 seconds and count the remaining requests.

timestamps = requests[user_id]
remove all timestamps older than now - 60 seconds
if len(timestamps) < 100:
    timestamps.append(now)
    allow
else:
    reject

Pros: Very accurate. No boundary burst issue.

Cons: Memory-heavy because every request timestamp is stored. Expensive for high traffic.

Use when: Accuracy matters more than memory, usually for low to medium scale.

Token Bucket

Idea: Each user has a bucket with tokens. Requests consume tokens. Tokens refill at a fixed rate. If tokens are available, allow. If not, reject.

tokens = min(capacity, tokens + elapsed_time * refill_rate)
if tokens >= 1:
    tokens -= 1
    allow
else:
    reject

Pros: Allows controlled bursts while enforcing average rate. Memory efficient: only store token count and last refill time per user.

Cons: Slightly less exact than sliding log. Requires careful timestamp/refill calculation.

Use when: Backend/API systems where controlled burst behavior is acceptable. Strong default for interviews.

Leaky Bucket

Idea: Requests enter a queue and are processed at a fixed rate. If the queue is full, new requests are rejected.

Pros: Smooth output rate. Good when downstream systems need predictable traffic.

Cons: Queueing adds latency. Less natural if you simply want allow/reject at the API edge.

Use when: You need to smooth traffic before sending to a downstream service.

Recommended Answer For 100 Requests/Minute/User

Pick Token Bucket for a product/backend interview unless exact fairness is explicitly required.

  • It allows small bursts, which is practical for real users and services.
  • It is memory efficient: store tokens and last_refill_time per user.
  • It works well with Redis for distributed rate limiting.

Tradeoff to mention: If strict accuracy is required, use Sliding Window Log or Sliding Window Counter, but memory and complexity increase.

Day 2 Interview Solutions: Rate Limiter Questions

1. Why Token Bucket instead of Fixed Window?

Answer: Fixed Window is simple, but it allows a boundary burst: 100 requests at the end of one minute and 100 at the beginning of the next. Token Bucket allows controlled bursts up to the bucket capacity while enforcing an average refill rate.

2. Why not keep counters on each application server?

Answer: Each server would see only part of a user's traffic. If a user is routed across five servers, they could exceed the global limit five times. A shared store such as Redis gives every server the same user state.

3. How do you prevent concurrent requests consuming the same token?

Answer: The refill, check, decrement, and state update must be one atomic operation. With Redis, use a Lua script or a suitable atomic command sequence. Never perform separate read and write operations without concurrency protection.

-- Conceptual atomic operation
read bucket state
calculate refilled tokens
if tokens >= 1:
    decrement token
    save tokens and timestamp
    return allowed
else:
    return rejected

4. What if Redis is unavailable?

Answer: Choose the policy based on the protected resource. For a payment or security-sensitive API, fail closed and reject or temporarily limit requests. For a low-risk read API, fail open for a short period to preserve availability. Add alerts, timeouts, circuit breakers, and a local emergency limiter.

5. How do you support free and premium users?

Answer: Resolve a user's plan before the limiter runs. Pass a policy object containing capacity and refill rate. For example, free users may get 100 requests/minute and premium users 1,000 requests/minute. The algorithm remains unchanged; only policy data changes.

class RateLimitPolicy:
    def __init__(self, capacity, refill_rate):
        self.capacity = capacity
        self.refill_rate = refill_rate

policies = {
    "free": RateLimitPolicy(100, 100 / 60),
    "premium": RateLimitPolicy(1000, 1000 / 60),
}

6. How would you add Sliding Window without changing RateLimiter?

Answer: Define a common RateLimitStrategy abstraction with an allow() operation. TokenBucketStrategy and SlidingWindowStrategy implement it. Inject the chosen strategy into RateLimiter. This applies OCP and Strategy pattern.

class RateLimitStrategy:
    def allow(self, user_id, policy, now):
        raise NotImplementedError

class RateLimiter:
    def __init__(self, strategy):
        self.strategy = strategy

    def allow(self, user_id, policy, now):
        return self.strategy.allow(user_id, policy, now)

7. What metrics would you monitor?

  • Allowed and rejected requests by user, endpoint, and plan.
  • Rate-limit rejection percentage and HTTP 429 count.
  • Redis latency, errors, timeouts, and memory usage.
  • Hot keys, such as one abusive user or API key.
  • Decision latency added by the limiter.
  • Fallback-open and fallback-closed events.

Strong Interview Summary

"I would place the limiter at the API gateway or service boundary. I would use a Token Bucket strategy backed by Redis, with an atomic Lua script for refill and consume. The limiter would depend on abstractions for storage, policy, and strategy, allowing different algorithms and user tiers without changing the core flow. I would return 429 with Retry-After when rejected and monitor rejection rate, decision latency, and Redis health."

Day 4 Theory: Atomicity, Redis, and Failure Handling

Atomicity: Refill, check, decrement, and save must behave like one indivisible operation. Otherwise, two concurrent requests can both read the same token count and both receive permission.

Shared state: In-memory counters are incorrect with multiple application servers because each server sees only a fraction of the user's traffic. Redis provides a shared state store.

Redis Lua script: Put the token-bucket calculation inside one server-side script. Redis executes the script atomically relative to other Redis commands.

state = redis.get(user_key)
tokens, last_refill = state or (capacity, now)
tokens = min(capacity, tokens + (now - last_refill) * refill_rate)

if tokens >= 1:
    tokens -= 1
    redis.set(user_key, tokens, now)
    return ALLOW

return REJECT

Failure policy: Fail closed for payments, authentication, or abuse-sensitive APIs. Fail open briefly for low-risk read APIs when availability is more important than strict enforcement.

Observability: Monitor allowed/rejected requests, 429 percentage, Redis latency/errors, decision latency, hot keys, and fallback events.

Interview phrase: "I would make the decision atomic, centralize state in Redis, choose failure behavior based on business risk, and monitor both enforcement quality and dependency health."

Day 5 Theory: Parking Lot Object Model

Goal: Model a parking lot that accepts vehicles, assigns suitable spots, issues tickets, calculates fees, and releases spots when vehicles leave.

Clarify first: vehicle types, spot types, multiple floors, entry/exit gates, pricing rules, payment methods, and whether reservations are required.

Core entities: ParkingLot, ParkingFloor, ParkingSpot, Vehicle, ParkingTicket, Payment, and SpotAssignmentStrategy.

Responsibilities: The lot coordinates the workflow; floors own spots; spots know availability and compatibility; a strategy chooses a spot; tickets record entry state; payment calculates and records charges.

Design principles: Use composition for a lot containing floors, Strategy for spot selection, Factory for vehicle creation if needed, and DIP so pricing/payment implementations can change independently.

Common mistake: Putting parking rules, pricing, payment, and spot-search logic into one large ParkingLot class.

Interview phrase: "I would clarify requirements first, model stable domain entities, and isolate variable behavior such as spot assignment and pricing behind strategies."

✅ Solution: Parking Lot System

Assumed requirements: Multiple floors, spot types (Motorcycle, Compact, Large), one vehicle per spot, nearest-available spot assignment, time-based pricing, single payment on exit.

from abc import ABC, abstractmethod
from enum import Enum
from datetime import datetime


class VehicleType(Enum):
    MOTORCYCLE = "MOTORCYCLE"
    CAR = "CAR"
    TRUCK = "TRUCK"


class SpotType(Enum):
    MOTORCYCLE = "MOTORCYCLE"
    COMPACT = "COMPACT"
    LARGE = "LARGE"


# A spot can host a vehicle type if it matches or is larger (SRP: only tracks spot state)
SPOT_COMPATIBILITY = {
    SpotType.MOTORCYCLE: {VehicleType.MOTORCYCLE},
    SpotType.COMPACT: {VehicleType.MOTORCYCLE, VehicleType.CAR},
    SpotType.LARGE: {VehicleType.MOTORCYCLE, VehicleType.CAR, VehicleType.TRUCK},
}


class Vehicle:
    def __init__(self, license_plate: str, vehicle_type: VehicleType):
        self.license_plate = license_plate
        self.vehicle_type = vehicle_type


class ParkingSpot:
    def __init__(self, spot_id: str, spot_type: SpotType):
        self.spot_id = spot_id
        self.spot_type = spot_type
        self.vehicle: Vehicle | None = None

    def is_available(self) -> bool:
        return self.vehicle is None

    def can_fit(self, vehicle: Vehicle) -> bool:
        return vehicle.vehicle_type in SPOT_COMPATIBILITY[self.spot_type]

    def assign(self, vehicle: Vehicle) -> None:
        self.vehicle = vehicle

    def release(self) -> None:
        self.vehicle = None


class ParkingFloor:
    def __init__(self, floor_number: int, spots: list[ParkingSpot]):
        self.floor_number = floor_number
        self.spots = spots

    def find_available_spot(self, vehicle: Vehicle) -> ParkingSpot | None:
        for spot in self.spots:
            if spot.is_available() and spot.can_fit(vehicle):
                return spot
        return None


# Strategy pattern (OCP): swap this to change spot-selection behavior without touching ParkingLot
class SpotAssignmentStrategy(ABC):
    @abstractmethod
    def find_spot(self, floors: list[ParkingFloor], vehicle: Vehicle) -> ParkingSpot | None:
        raise NotImplementedError


class NearestAvailableSpotStrategy(SpotAssignmentStrategy):
    def find_spot(self, floors: list[ParkingFloor], vehicle: Vehicle) -> ParkingSpot | None:
        for floor in floors:
            spot = floor.find_available_spot(vehicle)
            if spot:
                return spot
        return None


class ParkingTicket:
    def __init__(self, ticket_id: str, vehicle: Vehicle, spot: ParkingSpot, entry_time: datetime):
        self.ticket_id = ticket_id
        self.vehicle = vehicle
        self.spot = spot
        self.entry_time = entry_time
        self.exit_time: datetime | None = None


# DIP: PricingPolicy is an abstraction; concrete strategies can change without touching ParkingLot
class PricingPolicy(ABC):
    @abstractmethod
    def calculate_fee(self, ticket: ParkingTicket) -> float:
        raise NotImplementedError


class HourlyPricingPolicy(PricingPolicy):
    def __init__(self, rate_per_hour: float):
        self.rate_per_hour = rate_per_hour

    def calculate_fee(self, ticket: ParkingTicket) -> float:
        duration = ticket.exit_time - ticket.entry_time
        hours = max(1, int(duration.total_seconds() // 3600) + 1)
        return hours * self.rate_per_hour


class PaymentProcessor(ABC):
    @abstractmethod
    def process_payment(self, amount: float) -> bool:
        raise NotImplementedError


class CashPaymentProcessor(PaymentProcessor):
    def process_payment(self, amount: float) -> bool:
        print(f"Collected cash payment: {amount}")
        return True


class ParkingLot:
    def __init__(
        self,
        floors: list[ParkingFloor],
        assignment_strategy: SpotAssignmentStrategy,
        pricing_policy: PricingPolicy,
        payment_processor: PaymentProcessor,
    ):
        self.floors = floors
        self.assignment_strategy = assignment_strategy
        self.pricing_policy = pricing_policy
        self.payment_processor = payment_processor
        self.active_tickets: dict[str, ParkingTicket] = {}
        self._ticket_counter = 0

    def park_vehicle(self, vehicle: Vehicle) -> ParkingTicket | None:
        spot = self.assignment_strategy.find_spot(self.floors, vehicle)
        if spot is None:
            return None

        spot.assign(vehicle)
        self._ticket_counter += 1
        ticket = ParkingTicket(
            ticket_id=f"T{self._ticket_counter}",
            vehicle=vehicle,
            spot=spot,
            entry_time=datetime.now(),
        )
        self.active_tickets[ticket.ticket_id] = ticket
        return ticket

    def unpark_vehicle(self, ticket_id: str) -> float | None:
        ticket = self.active_tickets.get(ticket_id)
        if ticket is None:
            return None

        ticket.exit_time = datetime.now()
        fee = self.pricing_policy.calculate_fee(ticket)

        if self.payment_processor.process_payment(fee):
            ticket.spot.release()
            del self.active_tickets[ticket_id]
            return fee

        return None

Why this design scales in an interview:

  • SRP: ParkingSpot only tracks occupancy; ParkingFloor only searches its own spots; ParkingLot only coordinates the workflow.
  • OCP: Add a new assignment strategy (e.g. nearest-to-entrance) or pricing policy (e.g. flat-rate) without modifying ParkingLot.
  • DIP: ParkingLot depends on SpotAssignmentStrategy, PricingPolicy, and PaymentProcessor abstractions, not concrete implementations — easy to mock in tests.
  • Extension points an interviewer will probe: reservations, multiple payment methods, spot pricing that varies by floor, concurrent parking requests (thread-safety on spot assignment).
Day 6 Theory: LRU Cache

Goal: Design a fixed-capacity cache that supports O(1) get(key) and put(key, value), evicting the Least Recently Used entry when capacity is exceeded.

Clarify first: Is capacity fixed at construction? Does get count as a "use"? Should put on an existing key update its value and refresh recency? Thread-safety needed?

Why a HashMap alone isn't enough: A HashMap gives O(1) lookup but has no notion of order/recency, so you can't efficiently find "the least recently used" key to evict.

Why a plain array/list alone isn't enough: You could track order in a list, but moving an accessed item to the "most recent" end requires O(n) shifting.

Core data structure: HashMap (key → node) combined with a Doubly Linked List (maintains recency order). The HashMap gives O(1) access to any node; the linked list gives O(1) removal/reinsertion at either end without shifting.

Responsibilities: Node stores key/value and prev/next pointers; LRUCache owns the HashMap, the linked list's head/tail sentinels, and capacity enforcement.

Design principles: Composition (cache is composed of a map and a list), encapsulation of list operations (_remove, _insert_at_front) so the eviction logic stays simple and testable.

Common mistake: Using a singly linked list (can't remove a node in O(1) without a previous-pointer reference) or forgetting to move a node to the front on get, which silently breaks the LRU ordering.

Interview phrase: "I combine a HashMap for O(1) lookup with a doubly linked list for O(1) reordering, so both operations stay O(1) even as the cache grows."

Project 1: Low-Latency Trade Order Processing API

Best for: Goldman Sachs, JPMorgan, Morgan Stanley, Citi, Barclays, Deutsche Bank.

Stack: .NET Core Web API, SQL Server, Redis, Kafka/RabbitMQ-style queue, Docker, structured logging.

Features:

  • Place order API with idempotency key.
  • Transaction-safe order persistence in SQL Server.
  • Outbox table for reliable event publishing.
  • Async order-status updates through message queue.
  • Redis cache for account/order lookup.
  • Audit log for every state transition.
  • Metrics: API latency, queue lag, failed publishes, SQL query duration.

Resume bullet angle: "Built a transaction-safe order processing API with idempotent writes, SQL Server-backed persistence, async event publishing, and audit logging to simulate low-latency financial workflows."

Project 2: Production-Grade Rate-Limited API Gateway

Best for: GCC backend/platform roles where reliability, abuse prevention, and observability matter.

Stack: .NET Core or Node.js, Redis, SQL Server/PostgreSQL, Docker, OpenTelemetry-style tracing/logging.

Features:

  • Token Bucket rate limiting per user/API key.
  • Redis Lua-script style atomic decision logic.
  • Different plans: free, premium, internal service.
  • HTTP 429 with Retry-After header.
  • Fail-open/fail-closed mode by endpoint risk level.
  • Correlation ID and structured logs for every request.
  • Dashboard-ready metrics: p95 latency, rejection rate, Redis timeout rate.

Resume bullet angle: "Designed a Redis-backed rate-limited API gateway with atomic token consumption, tiered policies, fault-mode handling, and observability hooks for production-grade backend reliability."

Build Project 1 first. It best matches Wall Street engineering language: transactions, idempotency, SQL Server, async events, auditability, and low-latency API design. HLD Theory: Requirements, Scale, and Trade-offs

Start with the interview flow, then study infrastructure concepts before opening a case study.

HLD Interview Flow

1. Clarify Requirements: Functional (create URL shortener?) + Non-functional (1M writes/sec? 99.9% uptime?)
2. Estimate Scale: QPS, storage, latency SLA, geographic distribution
3. High-Level Design: Components (API Gateway, services, databases, caches, queues)
4. Deep Dive: Data models, sharding strategy, caching policy, consistency model
5. Tradeoffs: SQL vs NoSQL, strong vs eventual consistency, replication strategy

Interview Gold: "I started by understanding requirements and scale, then chose technologies based on tradeoffs."

Core Concepts (Weeks 5–10)

Load Balancing

Types: Round-Robin (simple), Least Connections (even distribution), IP Hash (session affinity), Consistent Hashing
Tools: Nginx, HAProxy, AWS ELB, Kubernetes Service
When to use: Multiple servers; need to distribute traffic for horizontal scaling

Caching Strategies

Types: Read-Through (cache-aside), Write-Through (slow writes, consistent), Write-Behind (fast writes, risky)
Tools: Redis, Memcached
Key Tradeoff: Latency vs consistency. Read-behind → fast reads but stale data. Write-through → consistent but slower.

Database Sharding

Strategies: Range-based (user_id 1–1M shard 1), Hash-based (consistent hashing), Geographic (region-based)
Challenges: Hot shards, re-sharding costs, cross-shard queries
When to use: Single database can't handle scale (storage or QPS)

Message Queues

Types: Kafka (durability, streaming), RabbitMQ (flexibility), AWS SQS (managed)
Use Cases: Decoupling, async processing, event streaming, load leveling
Tradeoff: Adds latency but improves system resilience

Replication & Consistency

Models: Master-Slave (one writer), Multi-Master (multiple writers), Consensus (Raft, Paxos)
CAP Theorem: Pick 2 of Consistency, Availability, Partition Tolerance
Tradeoff: Sync replication (slow, consistent) vs Async (fast, eventually consistent)

Classic HLD Problems (Week 5+)

Week 5-6: URL Shortener (TinyURL)

Scale: 1M writes/sec, 10M reads/sec
Components: API Gateway, ID generator (Snowflake/UUID), Sharded DB, Cache
Design Decisions: Use consistent hashing for ID generation; Redis for hot URL caching; SQL for persistence
Interview Gold: "I used Snowflake ID generator for distributed unique IDs and Redis for cache with TTL."

Week 6-7: Distributed Logger

Scale: 100s of MB/sec ingestion, queryability across weeks
Components: Log collectors, Kafka (durability), Stream processors (Storm/Spark), Storage (Cassandra/S3)
Design Decisions: Kafka for high throughput; Cassandra for time-series storage; Elasticsearch for searching
Interview Gold: "I used Kafka for durability, parallel processing for fault tolerance, and time-series DB for efficient queries."

Week 7-8: Real-Time Chat System

Scale: 1M concurrent users, 10K msgs/sec per room
Components: WebSocket servers, Message queue (Kafka), Distributed cache (Redis), DB
Design Decisions: WebSockets for real-time; Redis for message ordering; DB for persistence
Interview Gold: "I used WebSockets for bi-directional communication, Redis for state management, and eventual consistency for scalability."

Week 8-9: Low-Latency Search / Trade Lookup Service

Scale: 100M+ documents, sub-100ms query latency
Components: Web crawler, Indexer, Inverted index (Elasticsearch), Query engine, Ranking
Design Decisions: Distributed crawling; parallel indexing; sharded search clusters
Interview Gold: "I separated crawling, indexing, and searching to parallelize and scale independently."

Key Tradeoffs (Interview Checklist)

Tradeoff Option A Option B When to Choose
Consistency Strong (sync replication) Eventual (async) Financial → strong; Social → eventual
SQL vs NoSQL SQL (structured, ACID) NoSQL (flexible, scale) Relational data → SQL; massive scale → NoSQL
Cache Invalidation TTL (simple) Event-driven (accurate) High freshness critical → event-driven
Processing Real-time (low latency) Batch (cost-effective) Time-sensitive (fraud) → real-time; reporting → batch
