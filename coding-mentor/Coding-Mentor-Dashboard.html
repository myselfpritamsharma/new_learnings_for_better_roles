def checkInclusion(self, s1: str, s2: str) -> bool:
    left = 0
    window = {}
    need = {}

    for ch in s1:
        need[ch] = need.get(ch, 0) + 1

    for right in range(len(s2)):
        window[s2[right]] = window.get(s2[right], 0) + 1

        if right - left + 1 > len(s1):
            window[s2[left]] -= 1
            if window[s2[left]] == 0:
                del window[s2[left]]
            left += 1

        if window == need:
            return True

    return False
Takeaway: For fixed-size sliding window, add the incoming right character, remove the outgoing left character, then compare frequency maps.

Pattern 1: Two-Pointer

Idea: Two indices moving strategically to avoid nested loops (O(n) vs O(n²)).
Problems: Valid Palindrome, Two Sum II, Container With Most Water, 3Sum
Key: Works on sorted arrays or when order property helps.
Status: 🟡 Yellow (1/3 solved)
Day 1 Theory: Two-Pointer + Valid Palindrome
Core idea
Keep two pointers, usually left and right. Move them based on what the comparison tells you. This avoids checking all pairs.
When to use
Palindromes, sorted arrays, pair sums, reversing, container/water problems, or cases where both ends carry useful information.
Interview language
"I can solve this in one pass by maintaining two boundaries and moving only the pointer that cannot contribute to the answer."
Valid Palindrome reasoning:
  • Ignore characters that are not letters/digits using isalnum().
  • Compare normalized characters using lower().
  • If both match, move inward. If mismatch, return False.
  • If the pointers cross without mismatch, the string is a valid palindrome.
def isPalindrome(s: str) -> bool:
    left, right = 0, len(s) - 1

    while left < right:
        if not s[left].isalnum():
            left += 1
        elif not s[right].isalnum():
            right -= 1
        elif s[left].lower() != s[right].lower():
            return False
        else:
            left += 1
            right -= 1

    return True
Complexity: O(n) time, O(1) space.

Pattern 2: Sliding Window

Idea: Dynamic window expands/contracts to find optimal subarray/substring in O(n).
Problems: Longest Substring Without Repeating Characters, Minimum Window Substring
Key: Use HashMap to track state; each element added/removed at most once.
Status: 🟡 Yellow (2/3 solved)
Day 2 Theory: Sliding Window + Longest Substring Without Repeating Characters
Core idea
Maintain a valid range [left, right]. Expand using right; if the window becomes invalid, shrink using left.
When to use
Longest/shortest subarray or substring problems where the answer is a contiguous block.
Window invariant
For this problem: the current window must contain no duplicate characters.
Reasoning:
  • Add s[right] to the frequency map.
  • If s[right] now appears more than once, the window is invalid.
  • Move left forward until the duplicate is removed.
  • Update max_len only after the window is valid again.
class Solution:
    def lengthOfLongestSubstring(self, s: str) -> int:
        left = 0
        max_len = 0
        freq = {}

        for right in range(len(s)):
            freq[s[right]] = freq.get(s[right], 0) + 1

            while freq[s[right]] > 1:
                freq[s[left]] -= 1
                left += 1

            max_len = max(max_len, right - left + 1)

        return max_len
Common bug: When shrinking, decrement freq[s[left]], not freq[s[right]]. The left character is the one leaving the window.
Complexity: O(n) time, O(k) space, where k is the number of distinct characters.

SOLID Principles (The Foundation)

1. Single Responsibility (SRP)

SRP: One Class, One Reason To Change

Meaning: A class should own one responsibility. If validation, database writes, email sending, and logging all live in one class, one change can break unrelated behavior.

Bad shape: UserService validates input, hashes password, inserts into DB, sends email, and logs events.

Good shape: Split into UserValidator, PasswordHasher, UserRepository, EmailService, and AuditLogger.

class UserService:
    def __init__(self, validator, hasher, repo, email_service):
        self.validator = validator
        self.hasher = hasher
        self.repo = repo
        self.email_service = email_service

    def register(self, email, password):
        if not self.validator.is_valid(email, password):
            return False
        password_hash = self.hasher.hash(password)
        self.repo.save(email, password_hash)
        self.email_service.send_welcome(email)
        return True

Interview line: "I separated responsibilities so validation, persistence, and notification can change independently and be unit tested separately."

2. Open/Closed (OCP)

OCP: Add New Behavior Without Modifying Stable Code

Meaning: Existing tested code should stay stable when new variants are added. Add classes, don't keep adding if/elif branches.

Bad shape: Cache.evict() has if policy == "LRU", elif policy == "LFU", elif policy == "FIFO".

Good shape: Use a strategy interface.

class EvictionPolicy:
    def evict(self, cache):
        raise NotImplementedError

class LRUEviction(EvictionPolicy):
    def evict(self, cache):
        pass

class LFUEviction(EvictionPolicy):
    def evict(self, cache):
        pass

class Cache:
    def __init__(self, capacity, eviction_policy):
        self.capacity = capacity
        self.eviction_policy = eviction_policy

Interview line: "Adding LFU or FIFO should not require modifying the cache core; I would inject the eviction strategy."

3. Liskov Substitution (LSP)

LSP: Subtypes Must Not Break Parent Contracts

Meaning: If code expects a parent type, every child type must behave safely under the same contract.

Bad shape: Penguin extends Bird but throws in fly(). Or ReadOnlyRepository implements save() but throws.

Good shape: Model behavior honestly. Use Movable, Flyable, ReadableRepository, WritableRepository.

class Logger:
    def write(self, message):
        raise NotImplementedError

class FileLogger(Logger):
    def write(self, message):
        pass

class ConsoleLogger(Logger):
    def write(self, message):
        pass

Interview line: "Any implementation of the interface should be usable without the caller needing special-case checks."

4. Interface Segregation (ISP)

ISP: Prefer Small Focused Interfaces

Meaning: Don't create one huge interface that forces every class to implement unused methods.

Bad shape: One DataStore interface with read, write, delete, scan, backup, restore. A read-only cache is forced to fake unsupported operations.

Good shape: Split by capability.

class Reader:
    def read(self, key):
        raise NotImplementedError

class Writer:
    def write(self, key, value):
        raise NotImplementedError

class ReadOnlyCache(Reader):
    def read(self, key):
        pass

Interview line: "I would expose only the capabilities each client needs, which keeps contracts smaller and implementations honest."

5. Dependency Inversion (DIP)

DIP: Depend On Abstractions, Not Concrete Classes

Meaning: High-level business logic should not create or depend directly on low-level infrastructure like MySQL, Redis, SMTP, or Kafka clients.

Bad shape: UserService directly creates MySQLDatabase(). Tests need MySQL, and switching DB requires code changes.

Good shape: Inject an abstraction.

class UserRepository:
    def save(self, user):
        raise NotImplementedError

class SqlUserRepository(UserRepository):
    def save(self, user):
        pass

class UserService:
    def __init__(self, repo: UserRepository):
        self.repo = repo

Interview line: "I depend on a repository abstraction so I can test with mocks and swap SQL/NoSQL implementations without touching business logic."

Today's LLD Theory: Rate Limiter

Rate Limiter Basics: What Problem Are We Solving?

A rate limiter controls how many requests a user, IP, API key, or tenant can make in a time interval. Example: 100 requests/minute/user.

  • Input: user ID / API key / IP + timestamp.
  • Decision: allow request or reject with HTTP 429 Too Many Requests.
  • State: request counters, timestamps, or token count per user.
  • Hard part: doing this fast and correctly under high traffic and distributed servers.
Fixed Window Counter

Idea: Count requests in a fixed time bucket, like 10:00:00 to 10:00:59. Reset when the next minute starts.

key = user_id + current_minute
count = redis.incr(key)
if count == 1:
    redis.expire(key, 60)
return count <= 100

Pros: Very simple, memory efficient, fast in Redis.

Cons: Boundary burst problem. A user can send 100 requests at 10:00:59 and 100 more at 10:01:00, effectively 200 requests in 2 seconds.

Use when: Limits do not need high precision.

Sliding Window Log

Idea: Store timestamps of each request. For every request, remove timestamps older than 60 seconds and count the remaining requests.

timestamps = requests[user_id]
remove all timestamps older than now - 60 seconds
if len(timestamps) < 100:
    timestamps.append(now)
    allow
else:
    reject

Pros: Very accurate. No boundary burst issue.

Cons: Memory-heavy because every request timestamp is stored. Expensive for high traffic.

Use when: Accuracy matters more than memory, usually for low to medium scale.

Token Bucket

Idea: Each user has a bucket with tokens. Requests consume tokens. Tokens refill at a fixed rate. If tokens are available, allow. If not, reject.

tokens = min(capacity, tokens + elapsed_time * refill_rate)
if tokens >= 1:
    tokens -= 1
    allow
else:
    reject

Pros: Allows controlled bursts while enforcing average rate. Memory efficient: only store token count and last refill time per user.

Cons: Slightly less exact than sliding log. Requires careful timestamp/refill calculation.

Use when: Backend/API systems where controlled burst behavior is acceptable. Strong default for interviews.

Leaky Bucket

Idea: Requests enter a queue and are processed at a fixed rate. If the queue is full, new requests are rejected.

Pros: Smooth output rate. Good when downstream systems need predictable traffic.

Cons: Queueing adds latency. Less natural if you simply want allow/reject at the API edge.

Use when: You need to smooth traffic before sending to a downstream service.

Recommended Answer For 100 Requests/Minute/User

Pick Token Bucket for a product/backend interview unless exact fairness is explicitly required.

  • It allows small bursts, which is practical for real users and services.
  • It is memory efficient: store tokens and last_refill_time per user.
  • It works well with Redis for distributed rate limiting.

Tradeoff to mention: If strict accuracy is required, use Sliding Window Log or Sliding Window Counter, but memory and complexity increase.

Core Concepts (Weeks 5–10)

Load Balancing

Types: Round-Robin (simple), Least Connections (even distribution), IP Hash (session affinity), Consistent Hashing
Tools: Nginx, HAProxy, AWS ELB, Kubernetes Service
When to use: Multiple servers; need to distribute traffic for horizontal scaling

Caching Strategies

Types: Read-Through (cache-aside), Write-Through (slow writes, consistent), Write-Behind (fast writes, risky)
Tools: Redis, Memcached
Key Tradeoff: Latency vs consistency. Read-behind → fast reads but stale data. Write-through → consistent but slower.

Database Sharding

Strategies: Range-based (user_id 1–1M shard 1), Hash-based (consistent hashing), Geographic (region-based)
Challenges: Hot shards, re-sharding costs, cross-shard queries
When to use: Single database can't handle scale (storage or QPS)

Message Queues

Types: Kafka (durability, streaming), RabbitMQ (flexibility), AWS SQS (managed)
Use Cases: Decoupling, async processing, event streaming, load leveling
Tradeoff: Adds latency but improves system resilience

Replication & Consistency

Models: Master-Slave (one writer), Multi-Master (multiple writers), Consensus (Raft, Paxos)
CAP Theorem: Pick 2 of Consistency, Availability, Partition Tolerance
Tradeoff: Sync replication (slow, consistent) vs Async (fast, eventually consistent)
